# GYM OS Connect — إعداد وقبول / Setup & acceptance

**Development only. No production activation was performed.** افتح «المتابعة والتكاملات والدعم» بحساب المالك أو مدير الفرع. تظهر الأولويات معًا، ويمكن البحث وفتح ملف العضو أو التركيز على SMS والتذاكر والأجهزة. نماذج الإضافة مطوية حتى تبقى البيانات المهمة أولًا. لا يظهر هذا القسم للاستقبال، وتمنع API عملياته أيضًا.

## SMS

1. وثّق موافقة العضو المستقلة على SMS. سحب الموافقة يلغي الرسائل المسودة والمعتمدة التي لم تدخل الإرسال؛ لا يسترجع رسالة سبق قبولها لدى مزود خارجي.
2. راجع قائمة قرب الانتهاء/الانتهاء، ثم جهز مسودة عربية أو إنجليزية واعتمدها. لا ينشأ اشتراك أو تحصيل آلي. الرسائل لنفس العضو والانتهاء لا تتكرر، حتى بعد الإلغاء؛ يتطلب تغيير سياسة إعادة المتابعة قرارًا لاحقًا.
3. يستخدم إعداد الخادم `GYMOS_SMS_CONNECTIONS` مصفوفة JSON، كل عنصر بالمفاتيح `owner`, `branch`, `account`, `token`, `from`, و`dailyLimit` اختياري (افتراضي 50). owner هو **storage key** للنادي، وليس بريدًا أو معرف مستخدم عاديًا. استخدم حسابًا/مرسلًا معتمدًا. لا تضع token في المتصفح أو المستودع أو ملف باكدج العميل.
4. `GYMOS_SMS_ENABLED=0` افتراضيًا. بعد موافقة مسؤول النشر وقبول بيئة الاختبار فقط، يمكن ضبطه إلى 1. الإرسال يتم بزر مستقل وتأكيد رسوم، عبر `/api/sms-dispatch` مع جلسة موظف مخول وtenant header وrevision. لا يوجد cron لإرسال SMS حاليًا.
5. تُحفظ حالة dispatching قبل الاتصال؛ تحفظ النتيجة submitted مع SID إذا قُبل الطلب. ليست هذه حالة delivered. عند timeout/رفض/نتيجة غير قابلة للتحقق، تحفظ uncertain بصورة تحفظية، ولا توجد إعادة إرسال تلقائية. إذا تعطل الحفظ النهائي تظل dispatching ويجب المصالحة مع المزود. المجهول والمرفوض محسوبان ضمن حد اليوم التحفظي. الحد عدد طلبات وليس حد تكلفة نقدية أو عدد أجزاء SMS.
6. اختبار القبول المطلوب: مرسل مصرح به لمصر، رقم اختبار بموافقة صاحبه، قبول طلب ثم إثبات التسليم من المزود، عربي/إنجليزي وترميز وأجزاء الرسالة، انتهاء العضوية بعد تجهيز المسودة، سحب الموافقة، إعادة الطلب والتزامن وحد اليوم، timeout ومصالحة SID، تسرب الأسرار والسجلات. لم ينفذ إرسال حقيقي في هذه الدفعة. Delivery callbacks وتقرير تسليم آلي ومصالحة إدارية ليست منفذة بعد.

## أجهزة البصمة والحضور

1. أضف اسم الجهاز ومعرف الشخص المحلي واربطه بعضو **نفس الفرع**. لا ترفع بصمات أو صورًا. يمكن تعديل mappings عبر أمر `engagement.device.save` مع كامل المصفوفة؛ نموذج الشاشة الأولي ينشئ ربطًا واحدًا ويمكن تعطيل الجهاز أو تفعيله. تحرير قائمة روابط كبيرة واستيراد مستخدمي الأجهزة واجهة لاحقة.
2. اختر طراز الجهاز وSDK رسميًا. يحتاج الجهاز الذي لا يدعم HTTPS/HMAC وسيطًا محليًا يقرأ أحداث التعرف ويحولها للعقد أدناه. هذا الوسيط/SDK لم يُنفذ أو يُختبر على جهاز فعلي هنا.
3. إعداد الخادم `GYMOS_DEVICE_BRIDGES` مصفوفة عناصر `device`, `owner`, `branch`, `secret`. device هو ID المحفوظ، owner هو storage key، secret عشوائي مستقل بطول 32 حرفًا على الأقل. `GYMOS_DEVICE_BRIDGE_ENABLED=0` افتراضيًا. لا تُشارك سر الجهاز بين ناديين أو جهازين. تعطيل الجهاز في حالة النادي يمنع طلباته حتى لو بقي السر في الخادم.
4. POST HTTPS `/api/device-events`، Content-Type application/json. الجسم الصارم فقط:

```json
{"eventId":"synthetic_event_001","personId":"sensor-person-42","direction":"in","at":"2026-10-25T09:00:00Z"}
```

الاتجاه `in` أو `out`. الرؤوس: `X-GymOS-Device`, `X-GymOS-Timestamp` (Unix seconds)، `X-GymOS-Signature` (lowercase hex HMAC-SHA256). يوقع **timestamp + نقطة + بايتات JSON الأصلية UTF-8**. نافذة قبول كل من التوقيع ووقت الحدث خمس دقائق. لا تُقبل هوية النادي/الفرع من الجسم. يستخدم الخادم الربط الثابت فقط. جسم أقصاه 2048 byte؛ لا استيراد تاريخي أو batch في هذا endpoint.
5. eventId ثابت عند إعادة المحاولة؛ نفس الحدث يرجع duplicate دون حضور جديد، ونفس المعرف بمحتوى مختلف يرفض. تعارض revision يرجع 409، ويمكن إعادة الحدث نفسه بتوقيع زمني صالح؛ لا تغيّر eventId. أحداث التعرف تمر بقواعد العضوية والشيفت وحد الزيارات الحالية. لا يفتح هذا الكود بابًا ماديًا.
6. اختبار جهاز فعلي مطلوب: عدم التعرف/التعرف الخاطئ، دخول وخروج، انتهاء وتجمد وحد الزيارات، تزامن كارت وبصمة، انقطاع شبكة وانتهاء نافذة الحدث، إعادة توقيع، سحب ربط وتعطيل جهاز وسر خاطئ ونادي/فرع آخر. تأخر الأحداث أكثر من خمس دقائق يتطلب مسار مصالحة منفصل، ولا يُعاد تسجيلها كأنها حضور الآن.

## تذاكر الدعم

سجل داخلي للنادي والفرع: موضوع وأولوية ومتابعات وإغلاق. لا إرسال بريد أو WhatsApp أو إشعار لفريق المنصة. لا مرفقات أو SLA أو تولي موظف دعم مركزي. لا تدخل كلمات مرور أو بيانات صحية. استعادة نسخة قديمة قد تعيد محتوى سجل التذاكر كأي بيانات تشغيل؛ سجل النشاط منفصل. عند إنشاء helpdesk مركزي لاحقًا يجب تفويض الوصول إلى تذكرة بعينها مع سجل وصول، لا منح حق قراءة مساحة النادي بالكامل.

## تخزين وعزل وقبول

الحقل الاختياري `engagement` محفوظ في metadata لحالة النادي الحالية. تحقق schema والمراجع والفرع والعضو والـrevision موجود؛ packets تحجب الحقل كله عن الاستقبال وتصفّيه حسب فروع المدير. لا تعيد الاستعادة موافقات/حالات إرسال/تمكين أجهزة تاريخية. لا SQL migration لهذه الدفعة، ولا تغيير على قاعدة إنتاج.

القراءات لا تزال تحمل مساحة النادي كاملة خادميًا؛ ليست هذه ترقية pagination أو إثبات سعة. قبل التوسع التجاري: حدود واحتفاظ للسجلات، فهارس/جداول خاصة، اختبارات استعادة وحمل ومراقبة، وتنظيم الوصول الفني والخصوصية. احصل على قبول النشر قبل تفعيل أي مزود أو جهاز.

English: SMS is approval-based, opt-in and provider-disabled by default, with durable send claims, per-branch request caps and no automatic retries after uncertainty. Provider acceptance is not delivery. Device ingestion is a signed normalized-event contract, not a tested vendor SDK or physical door controller. Tickets are tenant/branch-isolated internal threads, not a staffed central helpdesk. All external/hardware acceptance remains outstanding. Do not deploy or enable without approval.
